## なぜ今これを書き残すのか

初期フェーズでは「週次・月次のレポートを確実に生成すること」に集中し、
検索や大規模データ処理は意図的にスコープ外にしている。

ただし、**その割り切りの理由と、将来どこへ向かうつもりだったのか**を残しておかないと、
数ヶ月後に設計を見た人が「なぜファイル中心なのか」「なぜ検索がないのか」を判断できない。
このドキュメントは、その文脈を保存するためのもの。

## 構想1：過去記事の検索機能

### やりたいこと

蓄積した過去記事を検索できるようにする。

週次・月次のレポートは「その期間に何があったか」を伝えるものだが、
運用が続くと「あのテーマの記事、前にもあったはず」「この業界の事例をまとめて見たい」という
**横断的な参照ニーズ**が出てくる。現在の設計はここに応えられない。

### 検索の3段階

段階を分けて考える。下にいくほど実装コストが上がるが、価値も上がる。

| 段階 | 内容 | 想定される使われ方 |
|---|---|---|
| **(1) 絞り込み検索** | タグ・スコア・日付での絞り込み | 「不動産業界かつ顧客関連度が高い記事」「2026年上半期のガバナンス系」 |
| **(2) 全文検索** | 記事本文・要約のキーワード検索 | 「"エージェント" を含む記事」 |
| **(3) 類似記事検索** | 意味の近さによるベクトル検索 | 「この記事と似た論点の過去記事」「表現は違うが同じテーマのもの」 |

(1) は構造化データへのクエリなので比較的軽い。
(3) は埋め込みベクトルの生成・保存・近傍探索が必要になるため、段階的に進めるのが現実的。

### 技術的な見通し

**全文検索・ベクトル検索はいずれも PostgreSQL が得意とする領域。**

- 全文検索：PostgreSQL の全文検索機能（`tsvector` / GIN インデックス）
- ベクトル検索：**pgvector** 拡張による近傍探索

検索エンジンを別途立てる（Elasticsearch 等）選択肢もあるが、
データ量の見通しと運用コストを踏まえると、**PostgreSQL 1つで完結させる**構成が第一候補。

> **この機能が、本番で PostgreSQL を採用する主要な動機になる。**
> 逆にいえば、検索機能を作らないのであれば PostgreSQL である必然性は薄い（→「現在の割り切り」参照）。

## 構想2：記事データの DB 蓄積（構想1の前提）

### 現在の設計とのギャップ

現在の設計は **「中間ファイル（xlsx）が正」**（設計書 §8・§13.4）。

この方針は**週次・月次のレポート生成には最適**で、意図的にそう決めている。

- 顧客指定の既存 xlsx と同形式の中間ファイルを生成する要件（仕様書 §8）を素直に満たせる
- HTML 生成（PROMPT-3）が xlsx を入力として読む前提と 1:1 で対応する
- ファイルがそのまま成果物・受け渡し単位・バックアップになる

一方で、**過去記事の横断検索には向かない。**
「直近2年分から特定タグの記事を探す」ような操作は、
**xlsx ファイルを1つずつ開いて全シートを走査する**ことになり、件数に比例して遅くなる。
インデックスも張れない。

### 検討する設計追加

検索機能を本格化する際は、**記事を検索用に DB のテーブルへも蓄積する**設計追加を検討する。

xlsx を捨てるのではなく、**xlsx は成果物として維持しつつ、DB を検索用の読み取りビューとして併置する**形が素直だと考えている（どちらを正とするかは着手時に再検討）。

### 現在の設計が土台として活きる点

重要なのは、**現在の設計がすでに検索に必要な構造をほぼ持っている**こと。

フィルタリング段階（設計書 §6）で、各記事には以下が構造的に付与されている。

- **10種の必須タグ**（情報カテゴリ / AIテーマ / 業界 / 業務領域 / 情報種別 / 地域 / 信頼性 / 顧客関連度 / 実務活用可能性 / レポート採用区分）
- **6軸のスコア**（0-100点）
- **情報カテゴリ**（7種）
- **収集日・URL・ソース**

つまり、構想1の **(1) 絞り込み検索に必要な項目はすでに揃っている**。
DB へ移すだけで (1) は成立し、(2)(3) は本文・要約に対する索引付けを足す形になる。

**現在ファイル中心で進めることは、将来の検索機能を捨てることを意味しない。**

## 構想3：SSO（OIDC）連携

> **格下げの記録：2026-08-13。** もともと SSO は「構想」ではなく**前提**だった（仕様書 §1.3「認証基盤の新規構築は含まない＝既存SSO前提でよい」／設計書 §3.1「認証は既存 SSO 前提」）。
> 方針変更により、**SSO 連携はやらず、ID/PW 認証を自前で実装する**ことが確定したため、ここへ移した。
> 現在の実装方針は [TASKS.md](../TASKS.md) §1.1「認証」「ログイン状態の保持」＋「備考：SSO 前提からの差分」が正。

### なぜ前提から降ろしたのか

1. **社内IT担当への確認待ちがボトルネックだった。** 連携方式（IdP の種類・クレーム設計・リダイレクト URI の登録手続き）が決まらないと着手できず、認証が「開発用スタブのまま」で止まっていた。認証が仮のまま認可（§6.2）や Config API を積み上げるのは、**「config は admin 以外に存在も中身も返さない」という最重要要件**（仕様書 §2）に対して据わりが悪い。
2. **手元完結の方針と噛み合わなかった。** 外部 IdP への依存は「社内連携が不要で手元だけで動くものを最優先」（TASKS.md §1.1）と正面から衝突する。
3. **現時点の要件は自前認証で満たせる。** 必要なのは社内利用者のログインと3ロールの出し分けだけで、IdP でなければ実現できない要件（多要素認証・SCIM プロビジョニング・他システムとのシングルサインオン・退職者アカウントの一括失効）は挙がっていない。

### 将来 SSO をやるとしたら

**「いつか SSO に戻すかもしれない」ための余地は残してある。**

- 認可（TASKS.md T-09）は `Principal`（ロール＋ユーザ識別子）だけに依存し、**「リクエスト → `Principal`」の解決は `AuthenticationBackend` プロトコルの内側**に閉じている。SSO 実装を1つ足して DI を差し替えれば、認可側は無変更で済む
- ただし**差し替え口がある＝SSO 対応済み、ではない**。着手時には最低でも次を決め直す必要がある

| 論点 | 内容 |
|---|---|
| **ロールの正はどちらか** | 本アプリの `users.role` か、IdP のクレームか。IdP を正にするなら「admin が昇格させる」フロー（T-42）は IdP 側の管理画面へ移り、本アプリのユーザー管理 API は不要になる |
| **既存アカウントの扱い** | 自前認証で作った `users` 行を SSO の subject に紐づけるのか、作り直すのか。メールアドレスを結合キーにする場合、IdP 側のメール変更に追随できるか |
| **併存させるか** | SSO とパスワード認証を両立させるのか（社外協力者など IdP にアカウントを持たない利用者がいる場合）。併存させるとパスワードリセット・アカウント乗っ取り経路の検討が倍になる |
| **cron の認証** | 現在の設計ではサービストークン（TASKS.md T-41）。SSO 導入後もここは別経路のまま残る |

**着手のトリガーになりうる事象**：社内の IdP 統合方針が固まる／多要素認証が必須要件になる／退職者アカウントの一括失効が運用上の要求になる／利用者数が増えてパスワード管理の負担が無視できなくなる。

## 現在の割り切り（文脈の記録）

初期フェーズで「あえてそうしている」判断。**将来変える前提のもの**として記録する。

### データベース：当面は SQLite

- **理由**：Docker 不要で手元完結できるため。初期フェーズは PM のフィードバックを早く得ることが最優先で、環境構築の重さがボトルネックになるのを避けたい
- **将来**：本番運用時、および検索機能（構想1）を本格化する際に **PostgreSQL へ移行**する想定
- **移行を楽にするために**：SQLAlchemy のモデル定義に閉じ込め、DB 固有機能（`JSONB`・配列型・`tsvector`・pgvector 等）への依存を避けておく

> ✅ **2026-08-13 追記：この方針は正式決定済み。**
> 当初あった「リポジトリが PostgreSQL 前提（`asyncpg` / `compose.yml` / `database_url`）で食い違っている」という指摘は、
> **TASKS.md T-39** として正式にタスク化し、解消済み。
> 現在の実装方針は TASKS.md §1「確定済み設計方針」＋「備考：PostgreSQL 前提からの差分」が正。
> `compose.yml` は削除せず、**将来の PostgreSQL 移行用**として残してある。

### 成果物ストレージ：当面はローカルの `artifacts` フォルダ

- **理由**：クラウドストレージ（S3 / Google Drive 等）は現時点では導入しない。手元で完結させる
- **将来**：クラウドへの切り替えは **`ArtifactStore` の差し替えで対応**する（TASKS.md T-02）
- **そのための設計**：成果物のパス解決・読み書きをすべて `ArtifactStore` 経由に統一し、
  他のコードが直接 `open()` しないようにしておく。これが差し替え可能性の担保になる

### `config.json` の置き場：当面はローカルファイル（＝実質1人しか編集できない）

> **記録日: 2026-08-13。** 会社展開（本番は AWS 予定）に向けた申し送り。**いま実装するものではない。**
> 現在の確定方針は「**中間生成物はファイルが正、ローカルの `artifacts` に置く**」であり、
> `config.json` も **DB ではなく `ArtifactStore` 経由のファイル**として保存する（TASKS.md T-11）。
> DB に入れるのは **監査ログ・config 改訂履歴・ユーザー／セッションのみ**、という切り分けを維持する。

- **現状の制約**：アプリ・DB・`config.json` のすべてが**開発者の PC 上**にあるため、
  **事実上1人しか config を編集できない**。楽観ロック（`base_revision`）は実装済みだが、
  そもそも他の管理者がその `config.json` に到達できないので、競合が起きる余地がない。
  **試作段階の割り切りとして許容する**（PM のフィードバックを早く得ることが優先）。
- **AWS に載せるとき**：`config.json` の保存先を**共有ストレージ（S3 等）へ切り替える**ことで、
  **複数の管理者が同一の config を編集できる**ようになる。ここが「1人しか編集できない」制約の解消点。
- **切り替え方**：**`ArtifactStore` の実装差し替え**で対応する想定（ローカルフォルダ版 → S3 版）。
  `config.json` のパス解決・読み書きも `ArtifactStore` に閉じてあるので、
  上位（`ConfigRepository` / Config API / パイプライン）には手を入れない。
- **同時編集の競合対策は AWS 移行時に検討する**：複数の管理者が同時に config を編集する場合の扱い
  （後勝ち／楽観ロックの強化／ロック取得など）は、そのときに決める。**現時点では未実装でよい。**
  検討時の論点になりそうな点だけ記録しておく。

| 論点 | 内容 |
|---|---|
| **`revision` の正はどこか** | 現在はファイル（`config.json` の `meta.revision`）。共有ストレージ上で複数プロセスが同時に読み書きすると、「読んで比較して書く」の間に割り込まれうる（read-modify-write 競合）。DB の `config_revisions` を採番の正に寄せるか、ストレージ側の条件付き書き込み（S3 の precondition 等）を使うかの判断が要る |
| **原子的書き込みの担保** | ローカルは一時ファイル→`rename`（同一ファイルシステム前提）。オブジェクトストレージには `rename` が無いので、別の担保方法（単一 PUT・バージョニング）へ置き換える必要がある |
| **後勝ちを許すか** | 現在は `base_revision` 不一致を **409 で拒否**（後勝ちにしない）。複数管理者運用でもこの厳しさを保つか、UI 側で「他の管理者が更新しました。差分を確認して再送信」へ誘導するかは運用感の話になる |
| **履歴・監査との整合** | 改訂履歴（`config_revisions`）と監査ログは DB のまま。ファイルの正と DB の履歴が食い違わない書き込み順序（現在はファイル書き込み成功後に commit）を、共有ストレージでも成立させること |

### 認証：当面は自前の ID/PW 認証

- **理由**：外部 IdP への依存を作らず手元完結させるため。詳細は上の「構想3：SSO（OIDC）連携」
- **将来**：SSO が必要になった場合は `AuthenticationBackend` の実装を追加して差し替える
- **そのための設計**：認可は `Principal` だけに依存させ、認証方式を知らせない（TASKS.md T-08・T-09）
